# 답변 품질 평가

> **상태: 평가 도구 구현됨 (#31).** 개발 서버 실행 기록은 아래 3절에 있습니다(2026-10-01 모델 사용·미사용 모두 7/7 통과).

README의 대표 질문 7개로 답변 품질을 같은 기준으로 반복 평가합니다. 평가 기준은 모델 없이 코드로 판정하는 **결정적 기준**과, 보고서를 보고 사람이 판단하는 **검토 항목**으로 나눕니다.

## 1. 평가 세트

[`config/eval/questions.yaml`](../config/eval/questions.yaml)에 README 대표 질문 7개와 질문별 기대값을 둡니다. README 문구와 평가 세트 질문이 같은지는 단위 테스트가 확인합니다.

| id | 질문 | 실행할 에이전트 | 허용 의도 | 그 밖의 기대값 |
| --- | --- | --- | --- | --- |
| q1_server_status | 현재 서버 상태가 어때? | Server | status | 기준 구간 없음 |
| q2_memory_spike | 최근 30분 동안 메모리 사용량이 급증한 서버가 있어? | Server | anomaly, compare | 30분, 기준 구간 있음 |
| q3_network_or_db | 서비스 응답이 느려진 원인이 네트워크인지 DB인지 분석해 줘. | Service → (Network ∥ DB) | anomaly, compare | 기준 구간, 분야 간 교차 확인 |
| q4_db_pool | DB 커넥션 풀이 부족한 징후가 있어? | DB | status, anomaly | |
| q5_k8s_pods | 재시작이 반복되거나 Pending 상태인 Pod를 확인해 줘. | Kubernetes | status, anomaly | |
| q6_logs_traces | 오류가 증가한 시간대의 로그와 트레이스를 함께 분석해 줘. | Service | anomaly, compare | Loki·Tempo 근거 (설정에서 켜져 있어야 함) |
| q7_compare_30m | 직전 30분과 비교해서 현재 상태가 어떻게 달라졌어? | Server ∥ (Service → DB) | compare | 30분, 기준 구간 있음 |

- 기대값에는 실제 데이터 값(서비스 이름, 수치)을 적지 않습니다. 개발 환경 데이터는 시점마다 달라집니다.
- 허용 의도는 질문 해석이 실제로 만드는 값(status·compare·anomaly)만 쓸 수 있습니다(평가 세트 로더가 검증).
- q7처럼 분야를 특정하지 않은 비교·증가 질문은 직전 구간 비교가 가능한 분야(서버 자원·서비스·DB)를 실행합니다([architecture.md](architecture.md) 4.2절). DB Agent는 실행 계획상 Service 다음에 실행합니다. Kubernetes 상태·네트워크는 확인하지 않으며, 이 사실을 답변의 "가정"에 적습니다. 단순 상태 질문("현재 상태가 어때?")은 서버 자원만 봅니다.
- 모델로 질문을 해석하면 q7의 분야 선택은 모델이 분야를 비워 두는지에 달려 있습니다(지침에 명시). 모델이 분야를 추측해 넣으면 "에이전트 선택" 기준이 실패로 드러납니다.

## 2. 평가 기준

### 2.1 결정적 기준 (`src/infra_agent/evaluation/checks.py`)

| 기준 | 통과 조건 | 관련 원칙 | 성격 |
| --- | --- | --- | --- |
| 에이전트 선택 | 실행한 에이전트가 기대 집합과 정확히 같음 (미지원 분야가 없는지는 구조 점검: 현재 5개 분야가 모두 구현됨) | 필요한 에이전트만 선택, 단순 질문을 확장하지 않음 | 품질 신호 |
| 선행 관계 | 기대한 선행 관계(예: Service → Network·DB)대로 실행 | 선행 결과가 필요한 작업은 순차 | 품질 신호 |
| 의도 | 해석한 의도가 허용 목록에 있음 | 의도·시간 범위 해석 | 품질 신호 |
| 분석·기준 구간 | 분석 구간 길이, 기준 구간 유무 (기준 구간 위치·답변 구간 일치는 구조상 보장) | 모든 에이전트가 같은 시간 범위 공유 | 품질 신호 + 구조 점검 |
| 근거 일치 | 확인된 사실이 1건 이상이고, 조회 실패 근거만으로 말한 사실이 없음 (근거 ID 존재는 스키마가 보장) | 실제 조회 결과에 근거 | 품질 신호 + 구조 점검 |
| 데이터 소스 | 기대한 소스(Prometheus·Loki·Tempo)를 실제로 조회함(결과 없음 포함, 결과가 없던 소스는 내용에 따로 표시). 설정에서 꺼져 있거나 시간 부족으로 생략했으면 그 사유를 표시 | | 품질 신호 |
| 실패·데이터 부족 표시 | 실패·건너뛴 에이전트와 판단 결과(사실)가 없는 에이전트가 "확인하지 못한 영역"에 있음. 판단 결과가 없는 에이전트는 범위 안내·"이상 징후 없음" 외의 사유를 적고, "이상 징후가 없어 원인 후보 생략"을 붙이지 않음. (구조 점검: 조회 실패가 있는 에이전트를 성공으로 표시하지 않음, 일부 실패를 요약에 표시, 사실이 없는데 요약이 "이상 없음"이라고 하지 않음) | 데이터 부재를 정상으로 판단하지 않음 | 품질 신호 + 구조 점검 |
| 인과 단정 금지 | 요약·사실·원인 후보(모델 해석 포함)·교차 확인에 인과 단정 표현이 없음. 서술형과 명사형을 모두 봄("때문입니다·때문임", "원인입니다·원인임", "원인으로 확인", "원인은 …로 확인됨", "…로 인해 지연됨" 등). 부정·유보 표현("원인으로 확인되지 않음", "원인으로 판단하지 않습니다", "때문일 가능성")은 단정이 아님. (구조 점검: 분야 간 동시 발생 원인 후보에 "인과는 확인되지 않음"이 있음) | 시간상 동시 발생으로 인과를 확정하지 않음 | 품질 신호 (주로 모델 원인 후보) |
| 분야 간 교차 확인 | 기대한 질문에 교차 확인 결과가 있고, 서비스 이상 대상을 정하지 못한 상태(서비스 분석 실패·판정 결과 없음)가 아님 | | 품질 신호 |
| 비밀정보 미노출 | 답변 전체(조회식 포함)가 마스킹 규칙에 걸리지 않음 | 인증정보 미노출 | 구조 점검 |
| 조회·모델 예산 | 조회 수와 모델 호출 수가 설정 상한 이하 (실행 중에도 강제되므로 회귀 점검) | 예산 관리 | 구조 점검 |

- **품질 신호:** 실제 운영 데이터와 질문에 따라 통과·실패가 갈리는 기준입니다.
- **구조 점검:** 코드·스키마가 이미 강제하는 성질이 깨지지 않았는지 보는 회귀 점검입니다. 통과했다고 답변 품질이 좋다는 뜻은 아닙니다.

결정적 기준을 모두 통과해도 답변이 좋다는 뜻은 아닙니다. 형식과 원칙 위반을 걸러 내는 하한선입니다.

### 2.2 사람 검토 항목

보고서의 "답변 원문"을 보고 다음을 메모합니다(보고서 끝 "사람 검토 메모").

- 요약이 질문에 직접 답하는가
- 사실·추정·데이터 부족이 구분되는가
- 원인 후보가 근거와 맞고, 추가 확인 제안이 실행 가능한가
- 과도하게 넓거나 빠진 내용이 있는가

## 3. 실행 방법과 기록

```bash
# 전체 7개 (모델 사용 여부는 설정을 따름)
infra-agent eval --config config/local.yaml
# 모델 없이 (규칙 기반 해석·코드 판정만)
infra-agent eval --config config/local.yaml --no-llm
# 일부 질문만 (id 또는 번호 부분: q3은 q3_…에만 맞음)
infra-agent eval --config config/local.yaml --only q3 --only q6
```

- 터미널에 질문×기준 표와 실패 사유를 출력합니다. 실패한 기준이 하나라도 있으면 종료 코드 3입니다(설정 오류 2와 구분). 모든 질문에서 분석이 실패하면(SSH 터널이 끊긴 경우 등) 평가 실패가 아니라 연결 문제로 보고 종료 코드 1입니다(Prometheus 비활성·보고서 저장 실패도 1).
- 상세 보고서(Markdown·JSON)는 `var/eval/`에 저장합니다. 실제 환경 데이터가 들어가므로 **커밋하지 않습니다**(`var/`는 Git 제외).
- 아래 기록에는 집계값과 실패 기준, 사람 검토 요약만 옮겨 적습니다. 서비스 이름·수치·로그 원문은 적지 않습니다.
